# PrintHub 整合分析 v1（2026-11-05，Muse 實讀正本 repo 程式碼）

## 結論先行
- 系統比白皮書寫的更單純：**後端只有一張表在工作**。所謂母子庫存、發放、對帳，全部是前端對同一張「講義工單紀錄」（25 欄）的不同看法，不是多張表。
- 真正的資產是**主旨協議的雙向性**：送印時組出來的標準主旨，可以反向從 Gmail 寄件備份整批解析回來重建資料庫——等於 Gmail 本身就是備份與歷史來源。這是設計上最聰明的一點，重塑或改版都不該弄丟。
- 已知弱點四個（設定沒存進資料庫、單表存發放名單、權限全開、Feiye0306 名下有舊版分身）。都不急，但要排進 Jules 的工作清單。
- 正本：`winnerseducenter/winner-course-material-system`（2026-10-09 版）。Feiye0306 名下的同名 repo 是舊版分身（停在 2026-10-01），之後要標明或封存，避免拿錯。

## 系統地圖
- 部署：容器綁定 GAS（綁在資料庫試算表上），執行身分＝部署者（winners.educenter@gmail.com），存取＝任何人（ANYONE），前端按鈕就可以操作，不需逐人授權。
- 後端 `Code.gs` 1,167 行、20 個函式；前端 `index.html` 2,323 行、Vue 3 單頁、6 個分頁：送印精靈（wizard）／母子庫存（inventory）／空間清理（cleanup）／核帳（reconcile）／發放名單（roster）／設定（settings）。
- 前端內建完整的本機模擬模式：沒有 GAS 時自動用假資料跑，雙擊 index.html 就能預覽全部流程。這對開發很重要——Jules 可以先在模擬模式改前端，不必每次都碰正式部署。

## 資料結構（以程式為準）
資料庫試算表「補習班講義印刷與發放數據庫」，實際用到的只有一張表：

**講義工單紀錄（25 欄）**：工單編號（ORD-日期-時間）、母講義名稱、是否加印、色彩規格、學用本數、教用本數、PDF頁數、交件日期、封面規格、特殊備註、郵件完整主旨、Gmail訊息ID、信件狀態、到貨狀態、到貨時間、已發放本數、單頁單價、裝訂費用、特殊加價、預估總金額、是否完成對帳、建立時間、附件檔案IDs、學生名單JSON、是否封存。

- 「母子關係」不是資料表設計：同一個母講義名稱的多筆工單（初印＋加印）在前端被歸成一張卡，庫存＝各工單本數加總－已發放本數。
- 發放名單以 JSON 存進工單那一列（第 24 欄），沒有獨立的發放紀錄表；誰領了、哪天領的，查不到歷史，只能看當下狀態。
- CONFIG 裡宣告了「班級名單暫存」與「系統全域設定」兩張表名，但後端從未建立或使用——**設定目前只活在前端**（廠商名稱／信箱、Drive 資料夾 ID、黑白 0.38／彩色 0.9／裝訂費預設值），換一台電腦或換瀏覽器就要重設。這是弱點 1。

## 後端函式地圖（20 個）
- 入口與資料庫：doGet、getOrCreateDb（三段式定位：指定 ID→容器綁定→自動新建，並自動補表頭到 25 欄）、formatDateSafe。
- 送印主線：sendPrintEmail（組主旨→掛附件→Gmail 寄出→回查 messageId→算預估金額→寫一列工單）、getOrders、markOrderReceived。
- Gmail 反向工程線：scanAndImportGmailHistory（掃寄件備份、依主旨與標籤整批匯入、標「講義已收到」者自動入庫）、parsePrintSubject（主旨解析器）、extractPdfPagesFromMessage／getPagesFromSinglePdfAttachment／extractPagesFromPdfText／getPdfPageCount（從信件附件反推 PDF 頁數）、repairZeroPageOrders（修復頁數為 0 的工單）。
- 清理線：getCleanupCandidates（已到貨＋有 messageId 者，量附件大小）、trashPrintEmail（信移垃圾桶、Sheets 紀錄保留）。
- 發放線：updateDistributionRoster（名單＋已發放本數寫回工單列）、saveMaterialDistributionRoster（以母講義為單位存名單）、updateMaterialPages（改頁數並重算金額）、toggleArchiveMaterial（封存切換）。
- 對帳線：markOrdersReconciled（工單逐列打勾）。注意：Excel 模糊配對與三色燈號是**純前端**運算，後端只負責最後打勾。

## 弱點清單（依重要性）
1. **設定不在資料庫**：全域設定表宣告了卻沒實作，設定只存前端。多人多機使用時會各自一份、互相不一致。
2. **發放無歷史**：名單 JSON 覆寫在工單列上，發放紀錄不可追溯；學生請假／補領只能看最後狀態。
3. **權限全開**：Web App 設 ANYONE＋ALLOWALL，拿到網址就能操作（含刪信、改庫存）。目前靠網址不外流在保護，規模小可接受，但要知道這件事。
4. **舊版分身**：Feiye0306 名下同名 repo 停在舊版（Code.gs 711 行 vs 正本 1,167 行），之後在那邊要標註「正本在 winnerseducenter」或封存，避免 Jules 或人拿錯版本施工。
5. 效能面目前無礙：所有查詢都是整表讀取，以現在的工單量（百筆級）完全夠快，不必先動。

## 與一對一案的關係
PrintHub 是「單一資料庫＋單一部署」的極簡樣本，正好是一對一重塑時「統一資料庫」路線的參照；一對一要走的是它的反面（各分校資料庫＋集中管理）。兩案共用同一個教訓：**設定與資料結構要寫成文件與程式內建初始化，不要只活在某台電腦或某個人腦裡。**
